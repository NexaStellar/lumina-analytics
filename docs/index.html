Current status

Prototype scaffold, not a running analytics product. The checked-in source currently includes a backend Horizon service, a backend package manifest, and a Docker Compose file. The referenced backend Dockerfile, frontend directory/Dockerfile, API server, database schema/migrations, and complete dashboard are absent from this checkout. Consequently the published README’s full-stack setup and feature list do not describe working code today.

This site distinguishes the implemented Stellar Horizon data-access methods from the intended future product. There is no current REST API or WebSocket server in the checked-in source. Do not rely on advertised dashboard URLs, API endpoints, alerts, export, database indexing, or Soroban analytics as implemented functionality.

Architecture and scope

The sole application service currently present is backend/src/services/horizon.ts. It wraps the Stellar SDK’s Horizon Server and exposes network reads and streaming. The project README describes a broader frontend/backend/database design, but those pieces must be built before that architecture exists.

Implemented nowHorizon transaction/ledger streaming, lookup, account reads, asset/trade/orderbook reads, and a basic recent-network summary.
Scaffold/config onlyPackage scripts and Compose service declarations for PostgreSQL/TimescaleDB, Redis, backend, and frontend.
Not implemented in this checkoutHTTP API, WebSocket routes, persistent indexing, UI, alerts, data exports, migrations, and operational authentication.

Setup and known limitations

The backend manifest targets Node.js 18+ and declares a dev script for src/index.ts, but that entrypoint is not present in the current file tree. The compose configuration references backend/Dockerfile and frontend/Dockerfile, neither of which is checked in, and there is no frontend/ directory.

For these reasons, docker compose up and the README’s backend start command are not currently a verified working setup. Treat the following as a starting point for the standalone service, not a full app launch:

cd backend
npm install
npm run typecheck

The package includes a typecheck script, but there are no checked-in backend tests or API entrypoint at this time. To use the service directly, construct HorizonService with a valid Horizon endpoint and a network label.

The service uses the Horizon SDK, not Soroban RPC. A SOROBAN_RPC_URL appears in Compose but no current service consumes it.

Usage patterns

Fetch a transaction

import { HorizonService } from './services/horizon';

const horizon = new HorizonService(
  process.env.HORIZON_URL ?? 'https://horizon-testnet.stellar.org',
  'testnet',
);

const transaction = await horizon.getTransaction(transactionHash);
console.log(transaction.hash, transaction.successful);

Stream and close a subscription

const close = horizon.streamTransactions(
  'now',
  (transaction) => console.log(transaction.hash),
  (error) => console.error('Horizon stream failed', error),
);

// When stopping the consumer:
close();

Use the lookup helpers

const account = await horizon.getAccount(publicKey);
const page = await horizon.getRecentTransactions(25);
const results = await horizon.search(publicKey);

These are direct service calls, not HTTP routes. The repository does not yet expose these methods to a browser client through an API server.

Configuration

The service itself takes its endpoint and network as constructor parameters; it does not read environment variables. The Compose file currently supplies these intended backend variables:

VariableCompose value / purpose
HORIZON_URLStellar testnet Horizon URL.
NETWORKtestnet; currently only used if application code passes it to the service.
SOROBAN_RPC_URLTestnet RPC URL declared in Compose; no Soroban service currently uses it.
DATABASE_URL, REDIS_URLIntended PostgreSQL and Redis connection strings; no checked-in code currently consumes them.
API_PORT, WS_PORTIntended API/stream ports; no checked-in server binds these ports.

Use your own infrastructure credentials and avoid committing environment files. The Compose file includes development database credentials and must not be used as a production secret configuration.

Operational behavior and error handling

  • Horizon calls can fail due to connectivity, endpoint limits, invalid identifiers, or missing records; callers should catch and surface errors appropriately.
  • Pass the optional stream error callback and always call the returned close function when the consumer is finished.
  • getNetworkStats() computes average fee and success rate from the returned transactions. An empty transaction page can result in non-finite summary values; validate the result before presenting it.
  • search() treats lookup failures as no results and does not provide ranked or fuzzy search. Its generic asset query is by asset code.
  • Configure CORS, authentication, rate limiting, and input validation before exposing any future server endpoints publicly.

Recommended implementation sequence

  1. Add focused tests for each HorizonService method and failure/empty-result behavior.
  2. Create a small backend entrypoint and a documented API contract, then wire selected Horizon methods through validated routes.
  3. Either implement the frontend and Dockerfiles referenced by Compose or remove the broken service declarations until they exist.
  4. Add database schema and indexing only after the required data model and retention needs are clear.
  5. Implement Soroban RPC integration separately from Horizon and document the distinct endpoints, network configuration, and failure modes.

This is a suggested sequence, not a claim that those components are already implemented.
